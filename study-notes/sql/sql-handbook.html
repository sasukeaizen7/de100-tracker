    Always ask "what is the grain?"

    Before writing a join or an aggregate, say out loud what one row of each table means. Most wrong numbers in real pipelines come from mixing grains (summing an order-level value on an item-level table).

    Logical order of execution

    You write SELECT first, but the database evaluates the clauses in this order:

    FROM / JOIN→WHERE→GROUP BY→HAVING→SELECT→window functions→DISTINCT→UNION→ORDER BY→LIMIT / OFFSET

    This order explains most "why doesn't this work?" moments:

    SymptomReasonFix
    A SELECT alias fails in WHEREWHERE runs before SELECTrepeat the expression, or wrap in a subquery / CTE
    An alias works in ORDER BYORDER BY runs after SELECT—
    Aggregates are not allowed in WHEREgroups don't exist yetuse HAVING
    Window functions are not allowed in WHEREthey are computed after WHERE and HAVINGfilter in an outer query (Postgres has no QUALIFY)
    LIMIT without ORDER BY returns "random" rowstables have no inherent orderalways order before limiting

    NULL and three-valued logic

    NULL means "unknown". Any comparison with NULL is itself unknown (NULL), and WHERE keeps only rows where the condition is true.

    ExpressionResultWhy
    NULL = NULLNULLtwo unknowns are not known to be equal
    NULL IS NULLtruethe only correct test
    NULL IS DISTINCT FROM NULLfalseNULL-safe comparison: treats NULLs as equal
    1 IS DISTINCT FROM NULLtrueuse it to detect changes in pipelines
    true AND NULLNULLcould be true or false
    false AND NULLfalsefalse whatever the unknown is
    true OR NULLtruetrue whatever the unknown is
    NOT NULLNULLthe opposite of unknown is unknown
    5 + NULLNULLarithmetic propagates NULL
    count(col), sum(col)ignore NULLscount(*) counts rows

    Subtotal NULL vs real NULL

    A subtotal row shows NULL in the rolled-up column, and so does a real NULL (the guest order has no city). grouping(col) returns 1 only for subtotal rows: use it to tell them apart, as above.

    Cross join and self join

    LATERAL

    Three join traps

    Fan-out: joining one order to its 3 items gives 3 rows. Summing an order-level amount after that join triples it. Aggregate to the right grain first, then join.

    Left join turned inner: LEFT JOIN orders o … WHERE o.status = 'paid' removes customers without orders (their o.status is NULL). Put the condition in ON to keep them.

    NULL keys never match: NULL = NULL is not true, so rows with NULL join keys disappear from inner joins.

    CTEs (WITH)

    A CTE names a subquery so a long query reads top to bottom, one step per CTE. It's the way dbt models and most production SQL are written.

    SubqueryCTETemp tableView

    Performance note

    Since PostgreSQL 12, a CTE used once is inlined like a subquery. Add AS MATERIALIZED to force it to be computed once (useful for an expensive CTE used several times), or AS NOT MATERIALIZED to force inlining.

    Recursive CTEs

    Two parts joined by UNION ALL: the anchor (starting rows) and the recursive part (refers to the CTE itself, adds rows from the previous step). It stops when a step adds nothing.

    Infinite recursion

    Always give the recursive part a stop condition (where depth < 10, a date limit). If the data can contain cycles (A manages B, B manages A), track visited ids in an array and stop when the next id is already in it, or use Postgres's CYCLE clause.

    Set operations

    Combine the rows of two queries with the same number of columns and compatible types (joins combine columns). Column names come from the first query.

    OperatorKeepsDuplicatesEquivalent pattern
    UNION ALLeverything from bothkept— (fastest: no dedup step)
    UNIONeverything from bothremovedSELECT DISTINCT over UNION ALL
    INTERSECTrows in bothremoved (INTERSECT ALL keeps them)EXISTS semi join
    EXCEPTrows in the first, not in the secondremoved (EXCEPT ALL keeps them)NOT EXISTS anti join
    NULLs in set operations

    Unlike =, set operations treat two NULLs as equal (like IS NOT DISTINCT FROM). That makes EXCEPT a quick way to diff two tables: (a EXCEPT b) UNION ALL (b EXCEPT a) lists every row that differs.

    Data engineering use

    UNION ALL stacks monthly files or several sources into one table. Choose UNION only if you really want dedup: it sorts or hashes the whole result.

    Autocommit

    Outside BEGIN, each statement is its own transaction. In psql, \set ON_ERROR_ROLLBACK on makes a failed statement inside a transaction not abort the whole transaction. In Python (psycopg), a connection opens a transaction automatically: call commit() or use with conn:.

    Repeatable readpreventedpreventedprevented in Postgrespossibleone snapshot for the whole transaction; may fail with a serialization error
    Serializablepreventedpreventedpreventedpreventedas if transactions ran one by one; retry on error 40001
    AnomalyWhat happens
    Dirty readyou read another transaction's uncommitted change, which is then rolled back
    Non-repeatable readyou read a row twice and get different values because someone committed in between

    Locks

    StatementLocksBlocks
    SELECTnothing on rows (MVCC: readers never block writers)only DROP/ALTER of the table
    UPDATE / DELETEthe changed rowsother writers of the same rows, until commit
    SELECT … FOR UPDATEthe selected rowsother FOR UPDATE and writers on those rows

    Deadlocks

    Session A locks row 1 then wants row 2; session B locks row 2 then wants row 1. Postgres detects it and kills one transaction. Prevention: always lock rows in the same order (e.g. ORDER BY id … FOR UPDATE) and keep transactions short.

    Partitioning and inheritance

    A partitioned table is one logical table stored as several physical tables. Queries that filter on the partition key read only the matching partitions (partition pruning), and dropping old data is a cheap DROP of a partition instead of a huge DELETE.

    Data engineering patterns

    The queries that come up again and again in pipelines and interviews.

    1. Deduplicate: keep the latest row per key

    2. Top N per group

    3. Period over period

    4. Gaps and islands: activity streaks

    Consecutive days minus a row number give the same value for every day of a streak: group by it.

    5. Sessionization

    A new session starts when more than 30 minutes passed since the previous event.

    6. Incremental load with a watermark

    Late data

    An event that arrives late with an old timestamp is skipped by a strict watermark. Real pipelines reload a safety window (occurred_at > watermark - interval '1 day') and rely on the upsert to avoid duplicates.

    Interview questions

    Try each one before opening the answer. Practise saying the reasoning out loud, in French and in English.

    1. Second-highest price (handle ties)

    Use dense_rank so two products tied for first don't hide the second value. Generalises to the Nth.

    2. Find and remove duplicate rows

    Find with GROUP BY key HAVING count(*) > 1. Remove with a self-join DELETE … USING keeping the smallest id, or with row_number() over (partition by key) and deleting rn > 1. If there's no id at all, Postgres's hidden ctid column identifies physical rows.

    3. Why can a LEFT JOIN return more rows than the left table?

    Each left row is repeated once per matching right row. A customer with 3 orders appears 3 times. It's the fan-out problem: check the grain, or aggregate the right side first.

    4. WHERE vs HAVING; UNION vs UNION ALL; DELETE vs TRUNCATE

    WHERE filters rows before grouping, HAVING filters groups after. UNION removes duplicates (extra sort/hash), UNION ALL doesn't. DELETE removes chosen rows one by one and fires triggers; TRUNCATE empties the table instantly.

    5. Running total and 7-day moving average

    sum(x) over (order by day rows between unbounded preceding and current row) and avg(x) over (order by day rows between 6 preceding and current row). Fill missing days with a date spine first, or the "7 rows" won't be 7 days.

    6. Users active on 3 consecutive days

    Gaps and islands: distinct (user, day), then day - row_number() over (partition by user order by day) is constant within a streak; group by it and keep count(*) >= 3. Alternative: lead(day, 2) = day + 2.

    7. Median without a median function

    Postgres: percentile_cont(0.5) within group (order by x). Portable: rank rows with row_number() and count(*) over (), then average the middle one or two.

    8. Why isn't my index used?

    A function or arithmetic on the column, a missing leading column of a composite index, a leading % wildcard, a type mismatch, stale statistics, or the planner correctly deciding a seq scan is cheaper (tiny table, many rows match). Check with EXPLAIN ANALYZE.

    9. View vs materialized view vs table

    A view stores the query (always fresh, no speed-up). A materialized view stores the result (fast, stale until refreshed, indexable). A table is maintained by your pipeline (incremental, can keep history).

    10. Function vs stored procedure

    A function returns a value and is called inside queries; it can't commit. A procedure is called with CALL, returns nothing, and can manage transactions (commit in batches).

    11. Explain isolation levels and a lost update

    See the transactions chapter. Postgres defaults to Read Committed. A lost update happens when two sessions read then write the same value; prevent it with an atomic UPDATE … SET x = x - 1, SELECT … FOR UPDATE, or Serializable with retries.

    12. How do you make a pipeline idempotent?

    Running it twice gives the same result as once: load into staging, then upsert/MERGE on a natural key (or delete-then-insert the partition being reloaded), inside a transaction. Never blind INSERT appends.

    13. SCD type 1 vs type 2

    Type 1 overwrites (no history). Type 2 closes the current row (valid_to, is_current = false) and inserts a new version with a new surrogate key, so facts keep pointing to the version valid at the time.

    14. OLTP vs OLAP, row vs column storage

    OLTP: many small transactions, row storage, normalized. OLAP: big scans and aggregations, columnar storage (reads only needed columns, compresses well), star schemas. That's why SELECT * is cheap in Postgres and expensive in BigQuery.
